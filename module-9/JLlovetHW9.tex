For questions 1 - 2, compare the efficiency of using sequential search on an ordered table of size n and an unordered table of the same size for the key \texttt{target}:
\medskip

\noindent\textbf{Problem 1:}
\medskip

\begin{enumerate}
  \item If no record with the key \texttt{target} is present.
  \item If one record with the key \texttt{target} is present and only one is sought.
\end{enumerate}


\medskip
\noindent\textbf{Answer:}
\medskip

\begin{enumerate}
  \item If no record with the key \texttt{target} is present.
        \begin{enumerate}
          \item Unsorted: If the table is unsorted, then it will be necessary to check all \texttt{n} items of the table to determine that no object has the key \texttt{target}. This means that we will have \texttt{n} comparisons to perform.
          \item Sorted: If the table is sorted, then we have a structural characteristic we can take advantage of. Let there be a value $k$ such that $k < n$ and $k \in \mathbb{N}$. If the first \texttt{k} keys are less than \texttt{target}, but there is a key $k+1 > \texttt{target}$, then it is only necessary to search the first $k$ items of the table. Essentially, we are partitioning the search space (the table) into values that are less than \texttt{target} and values that are greater than \texttt{target}. There will not be a value equal to \texttt{target} by hypothesis. If that partitioning results in two non-empty partitions, then we will save $n-(k+1)$ steps. Why $k+1$ and not $k$? Because we still have to do a comparison for the element immediately following $k$. For example, if we have a table \texttt{t} where $n = 8$, and if the element at index k=5 is less than target while values at indices $> 6$ greater than \texttt{target}, then we will examine the first 5 elements in indices $0,1,2,3,4$, but they we will have to do one more comparison to find that $\texttt{target} < \texttt{t[6]}$. Hence, we have to do 6 comparisons, and we will save $n-(k+1) = 8 - (5+1) = 2$ comparisons. In the best case, this means that we can short circuit comparisons after the first comparison. In the worst case, this means that we have to examine the entire table, as we did in th case where it was unsorted.
        \end{enumerate}
  \item If one record with the key \texttt{target} is present and only one is sought.
        \begin{enumerate}
          \item Unsorted: In the best case the key \texttt{target} will be in the first position, and in the worst case the key \texttt{target} will be in the last position. Considering each of the possible cases in order (namely that the key \texttt{target} is at position $k$), the cases will be orderable, which in turn means that we can create an enumeration of the cases with the natural numbers less than or equal to $n$. This enumeration corresponds to how many comparisons we have to perform to find \texttt{target} at the index one less than the value in the enumeration ($1$ comparison to find the element at index $0$, $2$ for finding it at index $1$, and so on). To take the average case, we can divide the sum of the first $n$ integers by the $n$ cases we have examined. Consider the sum of the first $n$ integers below.
                \begin{align*}
                  \sum_{i=1}^{n}i & = \frac{n(n+1)}{2}
                \end{align*}
                Dividing this by the $n$ comparisons, we obtain the average number of comparisons required:
                \begin{align*}
                  \frac{n(n+1)}{2} * \frac{1}{n} & = \frac{n+1}{2}
                \end{align*}
          \item Sorted: If the table is sorted, then we will unfortunately have the same average performance with sequential search as when it is unsorted. It still might be the case that the key \texttt{target} is at the final position or the first, and because by hypothesis the key is present, we cannot take advantage of short-circuiting in this analysis. We must compare each element in the table to \texttt{target} in turn, resulting in the same average performance of $\frac{n+1}{2}$ comparisons.
        \end{enumerate}
\end{enumerate}

\pagebreak
\noindent\textbf{Problem 2:}
\medskip

\begin{enumerate}
  \item If more than one record with the key \texttt{target} is present and it is desired to find only the first one.
  \item If more than one record with the key \texttt{target} is present and it is desired to find them all.
\end{enumerate}


\medskip
\noindent\textbf{Answer:}
\medskip

\begin{enumerate}
  \item If more than one record with the key \texttt{target} is present and it is desired to find only the first one.
        \begin{enumerate}
          \item Unsorted: In the worst case, there are two instances of the key \texttt{target}, and they are in the final two positions. In that case, we have to compare against $n-1$ elements to find the first instance of the key \texttt{target}. In the best case, the first element is the key \texttt{target}, and we are done. A similar analysis to the case above holds here too. Let $k$ represent the number of instances of the key \texttt{target}. Generalizing on the worst case, where all instances of the key \texttt{target} are at the end of the table, we save $k-1$ comparisons, compared to scanning the entire table. In general, we will have to check elements in positions $0 \le i \le n-(k+1)$. The average number of comparisons is derived in the same way as above, but now we will change the sum to be for the first $n - k - 1$ integers, and then derive the average number of comparisons from that. Specifically,
                \begin{align*}
                  \sum_{i=1}^{n - k - 1}i & = \frac{(n - k - 1)((n - k - 1)+1)}{2} \\
                                          & = \frac{(n - k - 1)(n - k - 1 + 1)}{2} \\
                                          & = \frac{(n - k - 1)(n - k)}{2}         \\
                \end{align*}
                To derive an average from this sum, we now have to divide by $n - k - 1$,
                \begin{align*}
                  \frac{(n - k - 1)(n - k)}{2} * \frac{1}{(n - k - 1)} & = \frac{n - k}{2}
                \end{align*}
                On average, if there are $k$ repetitions of the key \texttt{target}, we will have to perform $\frac{n - k}{2}$ comparisons.
          \item Sorted: In this case, the analysis is the same. It is possible in the worst case for the $k$ instances of the key \texttt{target} to be at the end of the table, requiring us to scan all of the elements up to the first instance, saving us $k-1$ comparisons, and it is possible for the first instance of the key \texttt{target} to be in the first position of the table, requiring only $1$ comparison. Intermediate cases are subsumed under the analysis above. This scenario overall similarly requires $\frac{n - k}{2}$ comparisons on average.
        \end{enumerate}
  \item If more than one record with the key \texttt{target} is present and it is desired to find them all.
        \begin{enumerate}
          \item Unsorted: In this case, all of the elements of the table must be scanned every time, since there is no way to know whether we have encountered all of the instances of the key \texttt{target} otherwise. Therefore, we have to make $n$ comparisons every time.
          \item Sorted: In this case, we have a more nuanced situation. We can short circuit once we have reached the end of the sequence of elements that have the key \texttt{target}. There can be $0 \le m \le n - k$ elements preceding the first instance in the sequence of $k \ge 2$ repetitions of the key \texttt{target}, and there are $s = n - m - k$ elements following the $k$ sequence of the $k$ instances of the key \texttt{target}. We will either hit the end of the table after the sequence of \texttt{target} keys, or we will have additional elements following them. In the second case, we only have to perform one comparison to find that we have left the target sequence, and then we can return. Consequently, we save $s-1$ comparisons in the sorted case.

                To give an example, let $t$ represent \texttt{target}. If we have a sequence $0,0,1,2,2,2,t,t,t,4,5,6,6,7$, then $n = 14$ because there are $14$ elements, $k = 3$ because there are $3$ repetitions of $t$, $m = 6$ because there are $6$ elements before the first instance of $t$, and $s=5$ because there are $5$ characters after the sequence of $t$'s. In this instance, we save $s-1 = 4$ comparisons, because we only have to compare against the element $4$ but not against the elements $5,6,6,7$.
        \end{enumerate}
\end{enumerate}

\noindent\textbf{Problem 3:}

Write a method \texttt{delete(key1, key2)} to delete all records with keys between \texttt{key1} and \texttt{key2} (inclusive) from a binary search tree whose nodes look like this:

  };
\end{tikzpicture}


\medskip
\noindent\textbf{Answer:}
\medskip

I am opting for a simple solution that is easy to reason about rather than a solution that uses clever manipulations of the tree. Perform an inorder traversal of the tree, and place elements from \texttt{key1} to \texttt{key2} in a queue. Then dequeue each node and delete it from the tree. It is likely that this is not an optimal solution, but its straightforward approach is attractive, because it could be used in other contexts as well, for instance to perform other operations on nodes with keys between two bounds.

\begin{minted}[linenos,breaklines,breakanywhere=true,fontsize={\fontsize{8pt}{9pt}\selectfont}]{Go}
function inorder(node) {
  // traverse the tree using the inorder traversal ordering
  // adapted from my lab3 python implementation that uses generators
  if node.left != null {
    yield from node.left
  }
  yield node.key
  if node.right != null {
    yield from node.right
  }
}

function delete(tree, key1, key2) {
  q = Queue()
  current = tree.root
  while current.key != key1 {
      current = inorder(current) // yields the inorder successor using the generator
  }
  while current.key != key2 {
      q.enqueue(current)
      current = inorder(current) // yields the inorder successor using the generator
  }
  q.enqueue(current) // handle the node with n.key == key2
  while !q.isEmpty() {
    toRemove = q.dequeue()
    tree, _ = remove(tree, toRemove.key)
  }
}
\end{minted}

For the function \texttt{remove(tree, node)}, we can use a function like the one below, adapted directly from \parencite{zybooks-ds2026}:

\begin{minted}[linenos,breaklines,breakanywhere=true,fontsize={\fontsize{8pt}{9pt}\selectfont}]{Go}
function remove(tree, key) {
   parent = null
   current = tree.root
   while (current != null) {
      // Check if current has an equal key
      if (current.key == key) {
         if (current.left == null && current.right == null) {
            // Remove leaf

            if (parent == null) { // Node is root
               tree.root = null
            }
            else if (parent.left == current) {
               parent.left = null
            }
            else {
               parent.right = null
            }
            return tree, true // Node found and removed
         }
         else if (current.right == null) {
            // Remove node with only left child
            
            if (parent == null) { // Node is root
               tree.root = current.left
            }
            else if (parent.left == current) {
               parent.left = current.left
            }
            else {
               parent.right = current.left
            }
            return tree, true // Node found and removed
         }
         else if (current.left == null) {
            // Remove node with only right child
            
            if (parent == null) { // Node is root
               tree.root = current.right
            }
            else if (parent.left == current) {
               parent.left = current.right
            }
            else {
               parent.right = current.right
            }
            return tree, true // Node found and removed
         }
         else {
            // Remove node with two children
            
            // Find successor (leftmost child of right subtree)
            successor = current.right
            while (successor.left is not null) {
               successor = successor.left
            }

            // Copy successor's key to current node
            current.key = successor.key
            parent = current

            // Reassign current and key so that loop continues with new key
            current = current.right
            key = successor.key
         }
      }
      else if (current.key < key) {
         // Search right
         parent = current
         current = current.right
      }
      else {
         // Search left
         parent = current
         current = current.left
      }
   }
   return tree, false // Node not found
}
\end{minted}
